## 3. Дефекты

### D-1. `internet.status` / `internet.label` вне контракта до завершения первого цикла — **minor**

- **Файлы:** `net-monitor/server.py` (`Monitor.snapshot()`, строки ~825–838); контракт `net-monitor/docs/api-contract.md` (строки 89–90). UI не затронут (`net-monitor/static/app.js:190`, `483–495` — unknown обрабатывается корректно).
- **Шаги воспроизведения:** запустить сервер с пустым `--data-dir`; сразу (первые ~0,25–8 с, пока идёт первый цикл) запросить `GET /api/state`.
- **Ожидание (контракт):** `internet.status` ∈ `ok | degraded | down`; `internet.label` ∈ {«Интернет работает», «Интернет нестабилен», «Похоже, интернета нет»}.
- **Факт:** `{"status": "unknown", "label": "Проверка не выполнялась", "latency_ms": null}`.
- **Воспроизводится:** `python3 tests/test_api.py --cold-start` (проверки `D-1`/`D-1b`, ~8 с окно).
- **Влияние:** только соответствие документации; UI при `unknown` не показывает ложный аварийный баннер (баннер реагирует лишь на down/degraded) и рисует «Нет данных». Data-контракт для внешних потребителей нарушен кратковременно.
- **Рекомендация:** либо добавить `unknown` (и ярлык «Проверка не выполнялась») в контракт как легальное состояние «данных ещё нет», либо в `snapshot()` до первого цикла отдавать последнее известное/`down`; фронтенд менять не требуется.

### D-2. `next_check_in` завышен на длительность цикла (~8 с) — **minor**

- **Файлы:** `net-monitor/server.py` (`Monitor._loop()` строки ~507–516 — следующий цикл планируется как `start + interval`; `_do_round()` строка ~560 — `last_round_epoch` пишется в **конец** цикла; `Monitor.snapshot()` строки ~861–863 — `next_check_in = interval - (now - last_round_epoch)`).
- **Шаги воспроизведения:** подождать завершения цикла и опрашивать `/api/state` до старта следующего; либо `python3 tests/test_api.py` (проверка `[10]`, known defect D-2).
- **Ожидание:** к моменту старта следующей проверки `next_check_in` близок к 0.
- **Факт:** перед самым стартом цикла поле показывает **8,1 с** (при `poll_interval=15`, длительность цикла 8 с); плановый цикл фактически стартует на ~8 с раньше объявленного.
- **Влияние:** счётчик «следующая проверка через N с» в UI не доходит до нуля и «прыгает» на «идёт проверка». На корректность опроса/статусов не влияет.
- **Рекомендация:** хранить время **старта** последнего цикла (или вычислять `interval - (now - round_start)`) и клампить снизу нулём; при желании отдавать `0`, пока `checking=true`.

Иных дефектов (blocker/major/minor/cosmetic) не выявлено. Найденные особенности поведения — не дефекты:

- `POST /api/check` во время планового цикла ожидаемо возвращает `ok:false / already_running` (по контракту).
- После ручного `POST /api/check` планировщик может сразу запустить свой цикл (он ждал `round_lock`) — `checking` кратковременно снова `true`; это ожидаемо.
- `uptime_1h` у заблокированных сервисов = `0.0 %` (считаются только `ok`) — соответствует смыслу поля.
- `services_affected` включает `degraded/blocked/down`, не `unknown` — соответствует контракту.

## 4. Покрытие и ограничения

**Покрыто:** запуск/остановка, все эндпоинты контракта (включая невалидные параметры, клампы, 404, заголовки), глубокая валидация схемы и enum'ов, согласованность summary/журнала/снимка, реальная сетевая картина (DPI-блокировки YouTube/Telegram), классификация всех веток, жизненный цикл инцидентов, серверный поиск/фильтры/пагинация, экспорт, персистентность через SIGTERM-рестарт, UI-рендер и все интерактивные элементы (поиск, фильтры, кнопка проверки, офлайн-баннер), обновление данных, консольные ошибки, адаптивность на 390 и 1280 px.

**Не покрыто / ограничения:**

1. **Локальный charset/браузер:** UI проверен только в Chrome 156 headless (CDP); Safari/Firefox и реальные скриншоты/визуальная регрессия не проверялись (согласно заданию — только DOM-текст). Промежуточные брейкпоинты 900/1120/760/480 px не измерялись (сетка проверена на 390 и 1280 + наличие медиазапросов в CSS).
2. **«Показать ещё» (пагинация UI):** `INC_PAGE = 100`, в живом журнале 2–3 сбоя, поэтому кнопка скрыта и её клик не воспроизводился; API-пагинация проверена, логика скрытия (`inc-more`) и обработчик проверены статически.
3. **Закрытие инцидентов на живой сети:** сеть стабильно блокирует YouTube/Telegram, поэтому live-переход `active → resolved` не наблюдался; проверен синтетическими юнит-тестами и сохранением/восстановлением статусов при рестарте.
4. **Офлайн-баннер:** воспроизведён блокировкой `/api/*` на уровне CDP, а не остановкой сервера (чтобы не ломать прогон).
5. **Экспорт скачиванием:** тело и заголовки проверены по HTTP; фактическое скачивание/парсинг файла браузером не выполнялось.
6. **Ввод в поиск:** эмулировался событием `input` через CDP (тот же обработчик и debounce 300 мс); дополнительно перекрёстно проверялся Playwright-сценарием REA — на запрос ушёл `GET /api/incidents?q=таймаут&…` с ответом 200.
7. **Долгий прогон** (часы, лимит series 24 ч / 8640 точек, ротация 500 инцидентов) не проверялся — только несколько десятков циклов.
8. **Кроссплатформенность бэкенда:** только macOS + Python 3.9.6; Windows/Linux не проверялись.
9. Результаты сетевых проверок зависят от провайдера/сети — картина «TLS/TCP-таймауты» актуальна для этой машины.
